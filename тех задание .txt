# GLOBAL OS

## Technical Specification / Project Charter v0.1

**Статус:** Initial Architecture Baseline
**Дата:** 21 сентября 2026
**Рабочее название:** `Global OS`
**Предыдущая концепция:** `Goal OS`
**Тип системы:** Durable Cognitive Runtime / Autonomous Work Operating System
**Целевой горизонт:** архитектура должна пережить смену моделей, agent frameworks, tool protocols и deployment technologies.

Главный принцип проекта:

$$
\boxed{
GlobalOS =
GoalContract+
EpistemicKernel+
DurableRuntime+
AuthorityKernel+
DynamicCognitiveOrganization+
WorldInteraction+
Verification+
Adaptation
}
$$

**LLM не является архитектурным ядром.**

LLM, reasoning model, coding model, multimodal model, future AGI — это interchangeable compute.

# 1. Миссия проекта

Global OS должна позволять человеку или организации задавать системе:

> **результат, ограничения, полномочия и критерии успеха**, а не пошаговые инструкции.

После этого система должна быть способна самостоятельно:

1. понять цель;
2. обнаружить неоднозначности;
3. сформировать Goal Contract;
4. построить модель задачи;
5. выбрать организационную структуру;
6. декомпозировать работу;
7. создать специализированные cognitive workers;
8. распределить полномочия и бюджеты;
9. исследовать проблему;
10. выдвигать и уничтожать гипотезы;
11. выполнять разрешённые действия;
12. собирать evidence;
13. независимо проверять результаты;
14. обновлять beliefs;
15. перестраивать план;
16. переживать сбои;
17. помнить прошлые решения;
18. учиться на ошибках;
19. запрашивать человека только там, где требуется authority или judgement;
20. продолжать работу часы, дни, недели и потенциально месяцы.

Цель:

$$
\boxed{
\text{max useful autonomous work}
\over
\text{unverified trust required from human}
}
$$

Не максимизировать количество tool calls.

Не максимизировать количество agents.

Не минимизировать human involvement любой ценой.

# 2. Что Global OS НЕ является

С самого начала зафиксировать `NON_GOALS.md`.

Global OS не является:

* chatbot wrapper;
* prompt library;
* фиксированным swarm из N agents;
* workflow engine с LLM внутри;
* vector database с memory;
* одной гигантской foundation model;
* replacement для Temporal;
* replacement для Kubernetes;
* replacement для IAM;
* MCP-only framework;
* системой, где model самостоятельно определяет собственные права;
* системой, где второй LLM автоматически считается verifier;
* системой, где `tool returned 200` означает success;
* системой, где каждый красивый result автоматически попадает в permanent memory;
* системой, способной самостоятельно менять production Authority Kernel.

# 3. Архитектурный горизонт

Система должна проектироваться так, чтобы:

```text
GPT-X исчез
→ Global OS продолжает существовать.

Claude-X исчез
→ продолжает.

MCP заменили
→ продолжает.

A2A заменили
→ продолжает.

Vector DB поменяли
→ продолжает.

Temporal заменили
→ возможно дорого, но domain model сохраняется.
```

Поэтому:

> **стабильными должны быть contracts и invariants, а не implementations.**

Современная индустрия уже движется в сторону long-running agents, durable environments и subagents; OpenAI Agents API, например, прямо ориентирован на агентов, работающих днями и сохраняющих intermediate state. ([OpenAI][1])

Temporal предоставляет соответствующую более общую durable-execution модель с восстановлением после process/network/infrastructure failure. ([Temporal][2])

Мы используем такие технологии как **текущие реализации interfaces**, а не как определение Global OS.

# 4. Architecture Constitution

Создать файл:

```text
CONSTITUTION.md
```

Это несущие invariants проекта.

### GOS-I01 — Intelligence ≠ Authority

Модель может предложить действие.

Она не может дать себе право его выполнить.

---

### GOS-I02 — No action without identity

Каждое действие связано с cryptographically/verifiably identified principal.

---

### GOS-I03 — No external effect without capability

Tool availability и permission должны быть разными понятиями.

Наличие email tool не означает право `email.send`.

---

### GOS-I04 — Child authority ⊆ parent authority

Delegation никогда не расширяет полномочия.

$$
Authority(child)\subseteq Authority(parent)
$$

---

### GOS-I05 — Model cannot modify Authority Kernel

Ни prompt, ни memory, ни tool output не могут изменить authority policy непосредственно.

---

### GOS-I06 — Goal cannot silently mutate

Любое изменение Goal Contract создаёт новую версию.

---

### GOS-I07 — Observation ≠ Belief ≠ Hypothesis ≠ Plan ≠ Commitment

Никакие эти сущности не должны храниться в одном generic `memory` object.

---

### GOS-I08 — Evidence shape ≠ evidence truth

Наличие URL, SHA, citation или marker не делает claim verified.

---

### GOS-I09 — Verification must have provenance

Любое `VERIFIED` должно отвечать:

```text
кем?
как?
чем?
когда?
относительно чего?
```

---

### GOS-I10 — Same model ≠ independent verification

Нужна verification diversity.

---

### GOS-I11 — Failed/null results are permanent knowledge

Отрицательные результаты нельзя тихо забывать.

---

### GOS-I12 — Invalidation propagates

Если доказательство потеряло validity:

```text
evidence invalid
→ dependent claim stale
→ dependent model stale
→ decision requires reevaluation
```

---

### GOS-I13 — External success must be reconciled

$$
ToolCallSuccess\neq IntendedWorldEffect
$$

---

### GOS-I14 — Material actions require Effect Receipt

Для существенного внешнего действия должна существовать postcondition verification.

---

### GOS-I15 — Recovery is normal execution

Crash/retry/replay — обычное состояние runtime, а не исключение.

---

### GOS-I16 — Unknown is valid

Система должна иметь first-class:

```text
UNKNOWN
INSUFFICIENT_EVIDENCE
CONFLICTED
UNVERIFIABLE
```

---

### GOS-I17 — Cost is part of reasoning

Вычисления, время, money, tool calls и human attention конечны.

---

### GOS-I18 — Management must justify itself

Новый organizational layer создаётся только при положительном ожидаемом value.

---

### GOS-I19 — Command authority ≠ epistemic authority

Руководитель подразделения не становится источником истины.

---

### GOS-I20 — Self-improvement is gated

Система может **предлагать и экспериментально проверять** собственные изменения.

Не может бесконтрольно self-modify trusted production core.

# 6. Архитектурный стиль: microkernel

Нужно избегать giant monolith и одновременно не начинать с 40 microservices.

Используем **logical microkernel / modular monolith + несколько жёстко изолированных security services**.

На старте:

```text
Python Runtime
 ├ Goal
 ├ Epistemic
 ├ Organization
 ├ Verification
 ├ Memory
 └ Model adapters

Rust Authority Service
 ├ authorization
 ├ capability enforcement
 ├ action normalization
 ├ approval verification
 └ effect protocol

Temporal
 └ durable workflows

PostgreSQL
 └ canonical structured state

Object Store
 └ artifacts

Sandbox Runner
 └ untrusted execution

Web Console
 └ user interface
```

Позже logical modules можно разделять физически без изменения contracts.

Это **reference implementation 2026**, а не вечная часть architecture.

| Зона                               | Baseline                                 |
| ---------------------------------- | ---------------------------------------- |
| Cognitive runtime                  | Python 3.13+                             |
| Security-critical Authority Kernel | Rust                                     |
| Durable workflows                  | Temporal                                 |
| Structured store                   | PostgreSQL                               |
| Artifact storage                   | S3/MinIO                                 |
| Policy language                    | Cedar                                    |
| Workload identity                  | SPIFFE/SPIRE-ready                       |
| Schema                             | JSON Schema + typed generated bindings   |
| HTTP contracts                     | OpenAPI                                  |
| Telemetry                          | OpenTelemetry                            |
| Tool protocol                      | internal Tool Contract + MCP adapter     |
| Remote agents                      | internal contract + optional A2A adapter |
| Sandbox MVP                        | container isolation                      |
| Strong sandbox later               | gVisor / microVM backend                 |
| UI                                 | TypeScript/React                         |
| CI                                 | GitHub Actions initially                 |
| Build provenance                   | SLSA-aligned                             |
| Secrets                            | dedicated secret manager abstraction     |

Cedar особенно подходит для маленького Authority Kernel: он специально отделяет authorization от business logic, использует `principal/action/resource/context`, default-deny semantics и имеет formal Lean model/validation work. ([Cedar Policy Language Reference Guide][3])

Для distributed identity интерфейс проектировать совместимым со SPIFFE; SPIRE уже предоставляет workload attestation и short-lived workload identities. ([Spiffe][4])

# 10. Goal Contract

`GoalContract` — first-class immutable versioned object.

Пример:

```yaml
goal_id: goal_medtech_001
version: 3

objective:
  text: >
    Найти наиболее реалистичную модель производства
    медицинского оборудования в Казахстане.

success_criteria:
  - id: sc_01
    description: at_least_three_viable_candidates

invariants:
  - no_binding_external_commitments
  - total_capital <= 8000000_USD

non_goals:
  - execute_investment
  - sign_contracts

forbidden_outcomes:
  - disclose_private_financial_data
  - contact_suppliers_without_approval

risk:
  tolerance: moderate
  maximum_irreversibility: none

authority:
  delegation_depth_max: 5

evidence_requirements:
  major_market_claim:
    verification_tier: 2

validity:
  starts_at: ...
  expires_at: ...
  reconfirm_after: 7d

termination:
  - success_criteria_met
  - user_cancelled
  - epistemic_stop_recommended_and_accepted
```

# 11. Goal amendment protocol

Goal никогда не перезаписывается.

```text
Goal v1
↓ amendment
Goal v2
```

Каждое изменение хранит:

```text
proposer
reason
changed fields
authority
approval
timestamp
impact analysis
```

Child goal не может ослабить parent constraints.

# 14. Bitemporal semantics

У epistemic entity должны быть минимум:

```text
recorded_at
known_at
valid_from
valid_until
observed_at
verified_at
```

Мы различаем:

> Когда мир был таким?

и:

> Когда Global OS узнала, что мир был таким?

Это крайне важно для replay и исторического reasoning.

W3C PROV уже даёт базовый язык entities/activities/agents и derivation provenance; мы используем этот принцип как foundation и расширяем его до reasoning provenance. ([W3C][5])

# 17. Confidence

Не заставлять модель ставить `0.73`, если probability не calibrated.

Два режима:

### Calibrated probability

Используется, только если имеется метод calibration/evidence.

### Epistemic confidence

```text
LOW
MEDIUM
HIGH
VERY_HIGH
```

и обязательное поле:

```text
confidence_basis
```

# 20. Authority Kernel

**Самый маленький и самый защищённый component.**

Модель не вызывается внутри Authority Kernel.

Вход:

```yaml
action_proposal:
  principal:
  goal:
  capability:
  resource:

  intended_effect:
  maximum_effect:

  reversible:
  information_disclosure:
  monetary_cost:

  idempotency_key:
  evidence_refs:
  approval_refs:

  context:
```

Выход:

```text
ALLOW
DENY
PENDING_APPROVAL
```

# 21. Почему отдельный kernel

Нельзя делать:

```python
if llm_says_safe:
    execute()
```

Нужно:

```text
Cognition
↓
normalized typed ActionProposal
↓
Authority Kernel
↓
execution token
↓
Tool Gateway
```

Tool Gateway **физически не должен принимать действие без execution token**.

# 28. Durable Runtime

# 79. Kill criteria H-ORG-001

Recursive architecture не принимается как default, если:

* не повышает success;
* error propagation растёт;
* management cost съедает выигрыш;
* summaries теряют evidence;
* dynamic topology стабильно проигрывает manager-worker;
* single strong agent дешевле при сопоставимом результате.

# 80. Основные research hypotheses проекта

Зафиксировать сразу.

### H-DUR-001

Durable execution значительно повышает long-horizon completion при failures.

### H-AUTH-001

External deterministic Authority Kernel снижает unauthorized-action rate без неприемлемого снижения task success.

### H-EPI-001

Typed epistemic state снижает factual contamination и stale-decision rate.

### H-VER-001

Verification routing превосходит generic LLM critic.

### H-ORG-001

Dynamic cognitive organization превосходит fixed topology для heterogeneous long tasks.

### H-MEM-001

Negative memory снижает повторные dead ends.

### H-CF-001

Counterfactual memory улучшает future decision calibration.

### H-VOI-001

VOI-aware planning снижает cost per successful decision.

### H-ADAPT-001

Governed procedural self-improvement даёт measurable gain без regression explosion.

# 100. Definition of Done v0.1

Первый milestone считается выполненным, если система может:

1. принять versioned Goal Contract;
2. построить task DAG;

4. выполнять задачи через Temporal;

6. после restart продолжить;
7. хранить observations отдельно от beliefs;
8. создать claim + evidence;
9. invalidation evidence автоматически пометит claim stale;
10. worker не сможет превысить parent authority;
11. запрещённое действие не достигнет Tool Gateway;
12. external canary action создаёт Effect Receipt;
13. event history позволяет replay;
14. все model calls идут через provider abstraction;
15. все tool calls идут через Tool abstraction;
16. basic OTel traces доступны;
17. budget ограничивает operation;
18. null result сохраняется;
19. один test сравнивает single-agent vs organization;
20. Survival Test с process kill проходит.

## Что я бы сделал первым коммитом

Не писал бы `agent.py`.

Первый repository commit должен содержать:

```text
README.md
CONSTITUTION.md
SPEC.md
ARCHITECTURE.md
THREAT_MODEL.md
AUTHORITY_MODEL.md
EPISTEMIC_MODEL.md
ORGANIZATION_MODEL.md
EVALS.md
ROADMAP.md
AGENTS.md
docs/adr/ADR-0001-system-boundaries.md
contracts/
```

**Второй** — CI и schema validation.

**Третий** — Event Ledger + Goal Contract.

**Четвёртый** — Authority Kernel.

И только после этого первый настоящий cognitive worker.

Это принципиально: если начать с «давайте запустим несколько агентов и потом достроим безопасность, память и evidence», почти наверняка получится ещё один agent framework. Если сначала построить **ядро состояния, полномочий, доказательств и воспроизводимости**, агенты затем станут обычными заменяемыми процессами внутри гораздо более фундаментальной системы.

Именно так я бы начинал Global OS.
